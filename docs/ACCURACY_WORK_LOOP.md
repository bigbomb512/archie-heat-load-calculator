# Archie heat-load accuracy work loop

Use this prompt when continuing accuracy work in this repository. It keeps the work moving through multiple tasks in the current active request; it does not run in the background or start a new chat turn after the current response ends.

## Objective

Improve the correctness, traceability, and usability of Archie’s heat-load calculations through complete, verified work. Do not make the user choose every next task. When asked to continue, or when asked “what’s next?” in the middle of this work, identify the highest-value task that can be completed from available project evidence and carry it out instead of returning only a recommendation.

## Repeatable cycle

1. Read the repository `AGENTS.md`, relevant method gates, source code, tests, and current accuracy records before deciding what to change.
2. Review the current state and identify the most consequential unresolved accuracy issue. Prefer work that can be completed and verified with information already available. Prioritize incorrect calculations or misleading results, then missing traceability, high-impact unsupported factors, and user-facing clarity.
3. Define the concrete outcome and acceptance checks for that task. Preserve its full authorized scope; do not substitute a report, prototype, or TODO for requested implementation.
4. Research authoritative and applicable sources when needed. Record the exact source, edition/date, relevant equation or condition, units, assumptions, and limitations. Do not infer that a field, UI control, or method gate means the factor is implemented.
5. Implement the selected task using existing project patterns. Keep separate design bases separate; do not invent project inputs, room geometry, source rights, engineer approval, or compliance status.
6. Verify the final change with meaningful tests, reference cases, browser checks, or other checks appropriate to the change. Re-run checks after the final edit. Report unavailable tooling and failed checks plainly.
7. Update the relevant documentation or project assessment with what changed, evidence, verification, remaining limits, and the next highest-value task.
8. **Continue within the current work block.** After a task passes its checks and its evidence/progress is recorded, select the next highest-value independently actionable task in the same block and carry it out without asking the user to say “continue.” Repeat the cycle until the block is complete or a stop condition below is met. Do not start another block in the same active request unless the user explicitly asks you to continue into another block.

## Work blocks

A **work block** is a bounded subsystem or major accuracy area, not an individual defect, test, or code edit. Examples include the complete outside-air and infiltration path, envelope and glazing gains, psychrometric state handling across cooling/heating/AHU consumers, or hourly room-load aggregation and its result reporting. A block usually contains multiple related tasks and should be broad enough to expose interactions between inputs, calculations, and reported results.

Do not declare a block complete after fixing one isolated issue. First audit its relevant input evidence and validation, resolvers, calculation methods, schedules/aggregation, method gates, report/API/UI, and existing benchmarks/tests. Include only layers that apply to that subsystem, but trace the result end to end. A useful starting boundary is one major load family or calculation workflow; split off a neighboring area only when it has a separate method, evidence base, and acceptance checks.

For each block:

1. Name the subsystem boundary and the end-to-end result it should produce. Inspect the applicable input/evidence, validation/resolution, calculations, aggregation, gates, report/API/UI, and tests before changing code.
2. Build a block checklist covering the relevant layers and interactions. Inventory concrete defects, missing verification, misleading status/provenance, and blockers; order implementable tasks by impact and evidence.
3. Complete the related tasks in the checklist as one sustained block. Verify each change, then re-audit the rest of the block for connected defects; a completed fix or passing suite alone does not complete the block. Do not invent values or silently broaden scope.
4. Consider the block complete only when all checklist items are fixed and verified or have precise external/professional blockers, no additional in-scope actionable issue remains from the audit, and the relevant end-to-end result path has been checked where applicable.
5. Record the subsystem coverage, changes, verification, and blockers; report the block outcome, then stop. Do not choose or begin another block automatically. The user can start the next block with a later request.

Keep a block large enough to cover a whole major accuracy workflow, but bounded by a coherent method and acceptance checks. Do not split one workflow into a chain of defect-sized blocks to stop early. If a discovered issue belongs to a distinct neighboring subsystem, record it for a later block unless the fix is required to verify the current block.

### Within-block continuation protocol

- At the start of each iteration, read the latest progress entry and inspect the current repository state; do not rely on a stale task list. Choose work that is valuable, testable, within the user's authorization, and supported by available evidence. Avoid duplicate work, artificial task splitting, and open-ended cosmetic churn. Continue until the major subsystem audit and its in-scope checklist are complete, rather than stopping after the first isolated fix.
- A task is complete only after its acceptance checks pass, the final edit has been re-verified, and the progress record states the result and remaining limits. Then choose the next task immediately. A failed check means fix or diagnose that task before advancing.
- A blocker on one task does not stop other independent tasks in the current block. Record the blocked task and why it is blocked, then continue within this block where possible; do not use it as a reason to start a different block.
- End work when the current block is complete, the user asks to stop, a consequential unresolved decision or external dependency blocks all useful remaining work in this block, no worthwhile independently actionable task remains in this block, or the active turn reaches a platform time/context limit. Do not claim the block is complete merely because one feature or test suite is complete.
- If the active turn must end before the block is complete because of a platform limit, update the progress log with the block name, in-progress task, checks still needed, blockers, and exact next task. On the next continuation, resume that block from the checkpoint rather than restarting or asking the user to choose.
- Once the block ends, send the final response with the block outcome, tasks completed, meaningful verification, material limitations, and any remaining blockers. Name a possible next block only as a suggestion; do not begin it automatically. Never imply that the loop continues unattended after the response.

## User interaction and stop conditions

- Do not repeatedly ask the user “what next?” or ask them to select routine technical tasks. Use repository evidence and engineering judgment to order work.
- Do not pause for permission for ordinary, reversible repository work already covered by the user’s request.
- Ask only when a decision materially changes product scope or engineering meaning and cannot be resolved from the project’s documented direction, or when a required input/access/approval is genuinely unavailable. Before asking, complete independent work and make the blocker specific.
- Stop the loop when the user asks to stop, when a hard external dependency prevents meaningful progress, or when remaining tasks require unavailable authorized source material or professional approval. Explain the exact blocker and what work is still possible.
- This prompt does not authorize external publication, contacting people, purchasing standards/data, or claiming engineer approval. Do not do those without explicit authorization.

## Accuracy and reporting rules

- Follow `AGENTS.md` and existing method/release gates. A passing test suite is evidence of software behavior, not proof of engineering validity.
- Keep preliminary estimates, draft weather data, fallback rates, and legacy/unverified inputs visibly labeled and traceable. Do not present sensitivity cases as one confirmed design condition.
- Keep room cooling distinct from plant sizing, code compliance, process exhaust, make-up air, transfer air, infiltration, and other separately scoped loads.
- Use independent reference values for calculation benchmarks when available. Do not generate expected values with the production function under test.
- Do not claim zero defects, complete accuracy, or production readiness. State what was verified and what remains unverified.
- For website changes, use `docs/BROWSER_TEST_LOOP.md` where applicable and verify the actual user flow after fixes.
